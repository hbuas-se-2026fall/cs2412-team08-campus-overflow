## 一、贡献

Lab7 阶段做的是把「没有测试」变成「有可执行的断言」。先后补齐了 co-shared-kernel 的 Guard、分页、时间、事件 ID 与角色异常测试；co-qa 四个聚合的访问器与重建用例；问答链路的集成测试，用 ArgumentCaptor 断言事件与审计副作用，而不是只看返回值。身份上下文补齐了课程、管理员、开放主机服务用例，行覆盖从 41.7% 提到 99.5%，这批经 #102 合并进 main。此外修了两处前端缺陷：课程成员请求缺失效守卫导致切课程后旧数据回填、用户管理页分页没有复用后端 size 造成前后不一致。

Lab8 承接「回归与缺陷登记」，产出四份东西：`regression-plan.md` 里定分层、准入准出与缺陷流转规则；`regression-checklist.md` 按九个业务域拆出 67 条可照做的用例，P0 11、P1 22、P2 27、P3 7；`lab8-defect-log.md` 从 D-09 起作为唯一台账；`env-readiness-report.md` 记环境核查与阻塞。

缺陷登记上真正花时间的是 D-08。它最初只写「CI 集成测试长期失败」，属于现象级描述，没法修也没法关。等到 #107 给 CI 加了报告归档，我把 `backend-test-reports` 拉下来解压，从 `failsafe-summary.xml` 拿到 `completed=2、errors=2、result=255`，再读两份报告确认 `CampusOverflowFlowIT` 0.024 秒、`QuestionInteractionIT` 1.063 秒，异常链是 `ContainerFetchException: Can't get Docker image: mysql:8.0.39`，底层 `Could not find a valid Docker environment`。到这一步才第一次有了「失败发生在容器启动、不是业务断言」的实证。

另外把错误码文档从 36 条补到 79 条，与源码双向核对差集为空；D-09 据此关闭，D-11 登记 Sonar 配置的两份事实源问题。

评审方面完成了 4 个未参与 PR。其中 #110 花了最多力气：作者把邮箱校验从嵌套量词正则改成手写分段，我用样例逐条比对新旧接受集合，发现两处收紧——域名 label 从允许下划线收紧为只允许字母数字连字符、单个 label 超过 63 字符被拒；同时确认原有测试只有 `not-an-email` 一条非法用例、新分支零覆盖，因此要求补参数化用例并把行为变更写进描述。补完后我复算了接受与拒绝两侧，确认 8 条拒绝各自命中不同分支、两条长度用例分别只由 label 上限与总长触发，才给的 Approve。

## 二、收获

最有价值的一条是：缺陷定论必须以可复现证据为前提。D-08 前后改了三版，从「原因未定位」到「定位到容器启动阶段」，再被评审指出「不能据此断言 runner 没有 Docker」后收窄为「配置层根因待诊断」。第三次修订不是退步，前两版把 Testcontainers 的自我判定当成了环境事实，而 runner 是 ubuntu-latest、本身就带 Docker。这个教训比修好一个缺陷更有用。

第二条是评审要能算，不能只读。邮箱那处如果只看 diff，会觉得「正则换成手写分段，语义等价」；只有把 `a@b_c.com`、`a@-b.com`、64 字符 label 这些样例代进新旧两套实现逐条跑，才能看出接受集合被收紧了两处，也才能判断这个收紧是修正还是回归。

第三条是分清阻塞与失败。67 条用例一条没执行，一开始会本能地想记成「未通过」，但按方案第七节，环境未就绪应记为阻塞，不写缺陷表，否则缺陷表会被环境问题污染。把「缺什么、谁提供、影响哪条准出条件」写清楚，比填一个假的通过率诚实，也更经得住评审追问。

## 三、改进

1. 定论过快。D-08 前两版都是在证据链没闭合时就下了环境级结论，后来靠评审纠正。之后改为「先取证、再定论、留证据行」，凡涉及环境判断，先给出取数命令与输出，再写结论。
2. 缺陷状态口径不严。原来 P1 只写「待修（某人）」，既没有排期窗口也没有关闭判据，按自己定的准出条件根本不算达标。现已统一为「已确认·已排期 + 责任人 + 关闭判据」，并注明若窗口内无修复提交要改判「待排期」。
3. 前置资源申请偏晚。回归的三项前置（子域名与 SSH、镜像分发、部署作业）到 Lab8 末段仍未到位，导致 67 条用例全量阻塞。改进方向是把前置清单在第一周就点到群里并留存确认记录，而不是等到要执行时才发现没有入口。
4. 合并顺序没有先对齐。声誉模块那批测试提交中途被撤回重做了一次，说明动手前没有先确认这块的归属与合并顺序。这类重复劳动本可以在开分支前用一句「这块谁在改、谁先合」避免。
