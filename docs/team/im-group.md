## 一、为什么必须有两条渠道

团队沟通分成两类，**走错地方会造成追溯断裂**：

| 类型 | 走哪里 | 原因 |
| --- | --- | --- |
| 日常同步、催办、约时间、临时求助 | **微信群** | 快，但需要可靠的到达率 |
| 一切技术讨论、方案决定、接口约定、评审意见 | **GitHub Issue / PR 评论** | 可追溯、可搜索、与代码同生命周期 |

> **红线**：群里讨论出结论后，必须回到对应 Issue 补一句结论再执行。
> 只在微信里口头定的方案，等于没定——回顾和答辩时查无实据。

## 二、建群操作（负责人执行）

1. 微信 → 右上角 `+` → 发起群聊 → 勾选其余 4 位成员；
2. 群名改为：`CampusOverflow · 计科2412班第5组`
3. 群公告粘贴 §三 的内容；
4. 把 §四 的自我介绍模板发到群里，@ 全员照格式回一条；
5. 打开「群管理 → 群聊确认」关闭，避免新人进不来；
6. 置顶两条聊天：① 仓库地址 ② 本文档地址。

**截图取证**（提交物需要）：

- [ ] 群成员列表截图（5 人头像 + 昵称清晰可见）

> 截图前请把**手机号、微信号等个人信息**裁掉——仓库是 Public。

## 五、备用渠道与升级路径

| 情况 | 怎么做 |
| --- | --- |
| 微信不可达 / 有人在群里超过 24 小时没回 | 在对应 Issue 里 `@` 该成员，GitHub 会发邮件通知 |
| 需要正式决策留痕 | 开一个 Issue，标题以 `[决定]` 开头，正文写背景、备选方案、结论、谁执行 |
| 分歧僵持超过 10 分钟 | 不消耗群里时间，直接升级到教师，并把结论写进 Issue |
| 请假 | 群里说明 + 在负责的看板卡片上备注，不算违约 |
