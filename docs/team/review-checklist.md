# 团队代码评审清单 v1.0

CampusOverflow　|　软件工程（2026 秋）　|　Lab 7 测试、代码评审与质量门禁　|　生效日期：2026 年 11 月 26 日

本清单依据课程教学方案 Lab 7 Step 4 制定，覆盖**正确性、可读性、可测性、安全、性能、风格**六个维度，用于每位成员评审自己未参与的 Pull Request。清单是人工复核依据，与 SonarQube / JaCoCo / Checkstyle / ESLint 等自动门禁互补：工具拦截格式、覆盖率、已知缺陷，人工重点判断业务规则、边界、上下文边界与可维护性。

适用范围：后端 `co-identity` / `co-qa` / `co-reputation` / `co-discovery`（api · application · domain · infrastructure · interfaces 五层）、`co-shared-kernel`、`co-bootstrap`，以及 `frontend/`（React + TypeScript）。

## 一、评审流程

1. **选 PR**：从本 Sprint 选 1 个自己未参与开发的 PR；先读对应故事（`docs/backlog/stories/`）验收标准、相关 ADR 与错误码约定，再读代码。
2. **先跑再评**：本地拉取评审分支，后端编译与单测、前端 `npm run typecheck` / `npm run lint` / `npm run build` 通过后再下结论；CI 因账户额度未跑起时，以本地结果为准并在评论中注明。
3. **逐项核对**：按第三节六维度过一遍，每条意见标注证据位置（文件：方法 / 行）。
4. **写实质意见**：每个 PR 至少 5 条实质性意见，按下述分级标注。
5. **给结论**：Approved（可合）/ Request changes（阻塞项未清，不可合）/ Commented（仅建议，不阻塞）。

### 意见分级

| 标签 | 含义 | 处理要求 |
| --- | --- | --- |
| 🔴 阻塞 | 功能错误、越权、上下文越界、会导致重复计分或数据不一致 | 必须修改后复审，未清不批准 |
| 🟡 建议 | 可维护性、可读性、测试补充、边界遗漏 | 应改，作者可在评论中说明不改的理由 |
| 🟢 可选 | 命名、措辞、后续优化 | 可排入后续 Sprint，不阻塞本次合并 |

### 意见写法（沿用章程“对事不对人，提意见必须带方案”）

一条合格意见包含四要素：**位置 → 问题 → 为什么是问题 → 建议方案**。

- 不合格：“这段代码写得不太好。”
- 合格：“`ReputationLedgerService.record`（位置）目前只按用户 + 原因查重，事件重放时同一事件可能重复入账（问题）；发件箱是至少一次投递，重复投递会让余额翻倍（为什么）；建议把 `eventId` 纳入查重键 `(event_id, user_id, reason)`，与账户唯一约束共同兜底（方案）。”

## 三、六维度检查清单

### 3.1 正确性（功能与需求一致）

- [ ] 故事验收标准逐条实现，正常路径、边界路径、异常路径都有对应逻辑，没有只覆盖主流程。
- [ ] 业务规则与指导书 / ADR 一致：投票每日上限按校园时区计数；采纳数与徽章对应；自问自答被采纳增量为 0、不写流水；悬赏缺少 sponsor 不发奖励；教师初始 1000 分、学生 0 分；排行榜结算可对账。
- [ ] 事件处理分支完整：每个事件类型都有对应分支，未覆盖的类型不会静默落入默认分支丢消息；内容删除事件须同时覆盖问题与回答两类目标。
- [ ] 幂等成立：开户按 `findByUserId` + 用户唯一键；记账按事件标识 + 用户 + 原因查重；徽章、排行榜、悬赏结算在事件重复投递或手工重放 `outbox_event.published_at` 置空时不重复变化。
- [ ] 空值与边界处理：`null`、空集合、非法枚举、不存在或越界 ID 有明确处理；计数与余额有防负保护（如 `GREATEST(..., 0)`）。
- [ ] 软删除生效：列表、详情、搜索、候选推荐均排除 `deleted = TRUE`；推荐候选排除问题自身与已删除内容。
- [ ] 一致性：余额、流水、徽章、悬赏结算在同一事务内完成；失败可回滚，发件箱事件与业务数据同事务提交。
- [ ] 前后端契约一致：字段名、类型、可空性与 OpenAPI 生成的 `src/api.ts` 一致，不手写漂移类型。

**本项目典型反例**：事件枚举漏一个分支；重放导致重复加分；候选 SQL 没排除自身或已删除；自答悬赏仍发奖励；教师 / 学生初始分写反。

### 3.2 可读性（他人能快速读懂并维护）

- [ ] 命名表达意图，领域术语与 `docs/ddd/glossary-v1.0.md` 一致；无拼音、无歧义缩写、无 `a2` / `tmp` 这类残留名。
- [ ] 分层归属正确：`domain` 只含纯领域模型与规则，不出现 JPA 注解、HTTP、框架依赖；`application` 编排用例、调用领域；`infrastructure` 实现接口；`interfaces` 只做协议适配（ADR-008、ADR-009）。
- [ ] 函数单一职责，长度与嵌套层级可控；重复逻辑抽取为共用方法，而不是复制粘贴。
- [ ] 注释解释“为什么这样定”（引用 ADR、验收标准、取舍），不复述“这一行在做什么”。
- [ ] 文档随代码同步：行为变更同步更新 ADR、错误码表、README 或接口说明；遗留 `TODO(S3)` 须注明负责人与去处。
- [ ] 一个 PR 聚焦一件事；提交信息可追溯到对应 PB / Issue，不混入无关改动。

**本项目典型反例**：domain 里直接依赖 Repository / JPA；跨上下文直接注入对方服务做同步查询；多个处理器复制同一段记账逻辑。

### 3.3 可测性（核心逻辑可被验证）

- [ ] 核心领域规则可脱离容器、数据库做单元测试；外部依赖通过接口注入，没有静态调用或硬编码环境耦合。
- [ ] 测试覆盖正常、边界、异常三类；核心聚合与计分 / 徽章 / 采纳规则有对应用例。
- [ ] 断言有效：断言结果状态、副作用、发出的事件；不用 `assertNotNull` 走过场；用 `ArgumentCaptor` 校验调用参数。
- [ ] 副作用可验证：发件箱事件、积分流水、徽章授予、悬赏退款都有对应断言，而不是只看方法不报错。
- [ ] 用例相互独立、可重复运行：不依赖执行顺序、不依赖固定外部数据；没有被改松的断言、没有为变绿而跳过的测试。
- [ ] 新增代码同步补测；通过删除或放宽断言让检查变绿属于学术诚信红线（章程二.5）。
- [ ] 覆盖率盲点有补齐说明；集成测试、契约测试标注所需运行环境（MySQL / Redis / Testcontainers）。

**本项目典型反例**：测试只 `assertNotNull` 返回值；处理器发了什么事件完全没断言；重复投递只测一次；边界用例（自投、重复采纳、悬赏已结束）缺失。

### 3.4 安全（鉴权、授权、输入与数据保护）

- [ ] 鉴权：未登录访问受保护接口被拒；会话基于 Redis 服务端会话（ADR-003），不自造令牌、不硬编码密钥。
- [ ] 授权：校验资源归属，只能修改本人资料 / 回答；非课程管理者、非提问者的操作返回 403，而不是默认放行。
- [ ] 输入校验：参数非空、长度、格式、枚举合法；前端提示不能替代后端校验。
- [ ] 注入防护：查询与命令全部参数化，不拼接用户输入；排序字段、筛选字段走白名单；无裸字符串拼 SQL 或正则注入。
- [ ] 越权访问：不能通过改路径 ID 读取或修改他人资源；软删除内容与他人流水不泄露。
- [ ] 敏感信息：日志不打印密码、会话、令牌；密钥不进仓库；不残留本机绝对路径、个人用户名等环境信息。
- [ ] 前端：渲染用户内容做转义防 XSS；`@昵称` 等提及按白名单正则解析；敏感信息不长期写入本地存储。

**本项目典型反例**：管理员接口只在前端隐藏、后端不判角色；用户输入拼进 SQL `LIKE`；日志打出完整会话；错误响应泄露内部堆栈路径。

### 3.5 性能（不引入可预见的瓶颈）

- [ ] 无 N+1：循环内不逐个查库或调远程服务；关联数据批量加载或由投影一次取出。
- [ ] 列表查询有分页或条数上限；不过度加载未使用字段；高频查询有对应索引（全文索引、状态字段等）。
- [ ] 循环内可合并的远程调用 / 缓存往返不重复发起；事件投影避免全表扫描。
- [ ] 排行榜、计数、采纳统计用聚合查询，不在内存里遍历全量集合。
- [ ] 缓存使用合理，失效后不出现陈旧数据；不做重复计算。
- [ ] 前端：长列表有分页或虚拟滚动；避免无关重渲染；请求具备加载态与错误态；复用契约生成的类型与请求封装。

**本项目典型反例**：在循环里按回答 ID 逐条查声誉；热门标签 / 排行榜每次全表 group by 无索引；列表一次拉全量再前端过滤。

### 3.6 风格（与仓库既有约定一致）

- [ ] 命名、包结构、模块归属遵循 ADR-009 与既有目录约定，不新造平行结构。
- [ ] 通过静态检查：后端编译 + ArchUnit 全绿；前端 `npm run lint`、`npm run typecheck` 通过；不绕过 husky 预提交钩子。
- [ ] 错误码归位：前缀按上下文 `ID-` / `QA-` / `REP-` / `DIS-` / `AUTH-` / `SYS-`，段位 `1xxx` 业务规则、`2xxx` 冲突、`3xxx` 权限、`4xxx` 未找到；异常类型与 HTTP 状态对应（422 业务规则、409 冲突、403 权限、404 未找到 / 已软删除），见 `docs/错误码.md`。
- [ ] 文件编码 UTF-8，无乱码；缩进、换行与 `.editorconfig` / Prettier 一致。
- [ ] 无调试残留：注释掉的代码、临时打印、临时代理地址、无用 import 已清理。
- [ ] PR 描述写清动机、改动范围、验证方式与关联 PB；评审意见与代码结论一致，不写与现状不符的“全绿”“已通过”。

**本项目典型反例**：错误码前缀张冠李戴；CSV / 文档用 GBK 保存导致导入乱码；前端联合类型未做 `in` 收窄直接取属性；评审稿声称 CI 全绿但 job 实际未启动。

## 四、跨上下文红线（评审必查，任一违反记 🔴）

1. **不跨上下文同步反查**：身份、问答、声誉、发现之间只通过事件与发布语言通信；消费方不注入对方应用 / 领域接口补查数据（ADR-001、ADR-002）。
2. **不跨上下文写库**：一个上下文不直接写另一个上下文的表；开户、结算等结果由本方聚合在自己事务内完成。
3. **事件负载自洽**：开户所需的用户标识、昵称、角色随事件携带，消费方不回查身份库；事件 schema 变更要同步消费方与 ADR。
4. **领域与持久化分离**：领域对象不被 JPA 实体污染；映射放在 infrastructure（ADR-008）。
5. **契约优先**：前端类型由 `scripts/gen-api.ts` 从 OpenAPI 生成，不手写与后端漂移的接口类型（ADR-007）。

## 五、评审记录与清单维护

1. 意见落在对应 PR 评论区；结论以 GitHub Review 形式提交（Approved / Request changes / Commented）。
2. 每份深度评审至少 5 条实质性意见，并保留评审记录（PR 评论导出 PDF 或截图），归入 Lab 7 提交物。
3. 本清单 v1.0 在 Sprint 3 末定稿；后续 Sprint 回顾会可根据评审中反复出现的问题增补条目，修订通过 PR 提交，版本号递增（v1.1、v1.2……）。
4. 清单条目与自动门禁分工：工具已自动拦截的（格式、未用变量、编译错误）不再重复提；人工意见聚焦工具判断不了的业务正确性、边界、上下文边界与设计取舍。
