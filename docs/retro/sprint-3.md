## 三、开始做

1. **骨架清零排期**：为剩余 31 个方法逐个建 Issue，指定负责人与截止日，未清零不算完成。
2. **拉取请求三日规则**：任何拉取请求停留超过 3 天，必须在每日站会上说明卡点与下一步。
3. **同模块开工前先认领**：动某个模块前先在群里报备，避免两人并行写同一批文件（本轮 #91 与 #92 的重复就是这么产生的）。

## 四、停止做

1. 停止把功能分支长期挂在远端不合：分支生命周期过长会持续制造合并冲突。
2. 停止把"已批准"当作"可合并"：批准只解决评审，检查未绿仍然合不了，必须两项都清。
3. 停止在主干上演示未合入的功能：评审会从 `main` 的最新提交启动，分支上的成果不算增量。

## 五、继续做

1. 继续用"事件 + 幂等"的方式做跨上下文集成：发件箱至少一次投递已被证明可靠，重放测试也在按这个思路补。
2. 继续保持先写测试再实现：本轮补内容发现领域层时，正是先读测试再写实现，5 个用例一次转绿。
3. 继续在合并请求里写清"对应问题编号 + 改动范围 + 验证方式"，评审成本明显下降。
