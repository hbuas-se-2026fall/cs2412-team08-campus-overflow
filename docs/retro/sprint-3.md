客观事实（已核实，可直接引用）：

- 主干 `main` 上的声誉模块处理器五个方法全部抛 `UnsupportedOperationException`，说明行走骨架未清零；
- 声誉实现分支 `feature/zhangjiayu-reputation-core`（拉取请求 #87）尚未合入，评审意见已提出一轮修改；
- 本仓库没有 `develop` 分支，功能分支直接对 `main` 提拉取请求；
- 团队成员本地 JDK 版本不一致（存在 JDK 26 环境），导致本地单元测试因 Mockito 不兼容整批报错，而持续集成使用 JDK 21 时可能是绿的。

## 三、开始做

1. **主干骨架清零排期**：为每个仍是 TODO 的方法建 Issue，指定负责人与截止日，未清零不算完成。
2. **拉取请求三日规则**：任何拉取请求停留超过 3 天，必须在每日站会上说明卡点与下一步。
3. **本地环境基线校验**：开工前统一确认 JDK 21、Docker 可用；环境不一致导致的"假红"要在站会当场排除。

## 四、停止做

1. 停止把功能分支长期挂在远端不合：分支生命周期过长会持续制造合并冲突。
2. 停止把"已批准"当作"可合并"：批准只解决评审，检查未绿仍然合不了，必须两项都清。
3. 停止在主干上直接演示未合入的功能：评审会从 `main` 的版本标签启动，分支上的成果不算增量。

## 五、继续做

1. 继续用"事件 + 幂等"的方式做跨上下文集成：发件箱至少一次投递已被证明可靠，重放测试也在按这个思路补。
2. 继续保持先写测试再实现：声誉与问答模块的领域测试已覆盖主要规则，是本轮质量的主要支撑。
3. 继续在合并请求里写清"对应问题编号 + 改动范围 + 验证方式"，评审成本明显下降。
