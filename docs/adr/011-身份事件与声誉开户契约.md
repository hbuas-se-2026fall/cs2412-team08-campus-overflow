# ADR-011 身份事件与声誉开户的契约

- 状态：提议
- 日期：2026-11-18
- 决策人：李增艳
- 相关代码：`co-identity-api` 的 `UserRegisteredEvent`、`co-reputation-application` 的 `ReputationEventHandlers`、`ReputationLedgerService`、`co-reputation-domain` 的 `ReputationRulebook`

## 背景

声誉模块的账户不由用户主动创建，而是被动地由身份上下文的事件驱动创建。身份上下文在两处发布 `UserRegisteredEvent`：

- `UserRegistrationService.register`：学生自助注册；
- `AdminUserService.createStaff`：管理员创建教职工账号。

两处都传入 `saved.role()`，事件签名是：

```
UserRegisteredEvent(String eventId, Instant occurredAt, long userId, String displayName, Role role)
```

声誉侧的处理规则来自实验指导书 6.4.3 与 6.4.4：

- 账户已存在则忽略（幂等），否则开户；
- 教师账号初始 1000 分，学生 0 分。

主干的 `ReputationEventHandlers` 目前是骨架，五个处理方法都抛 `UnsupportedOperationException`，因此任何触发注册事件的流程都会在下游处理时失败。实现版本位于 `feature/zhangjiayu-reputation-core`，尚未合入 `main`。

需要把这条跨上下文契约固定下来，避免后面两个 Sprint 反复改动。

## 决策

1. **事件携带角色，声誉侧不反查身份接口。**
   开户所需的一切信息（用户标识、昵称、角色）都由事件负载提供。声誉模块只依赖 `co-identity-api` 的事件类型，不注入 `IdentityApi` 做同步查询，保持上下文之间只经发布语言与事件通信。

2. **开户幂等由"查询 + 唯一键"两层保证。**
   处理时先 `accounts.findByUserId(userId)`，存在即直接返回；并发重复投递时由账户表的用户唯一约束兜底。发件箱是至少一次投递，不能假设事件只来一次。

3. **初始积分在开户时一次确定，之后不因角色变更回补。**
   初始积分由 `ReputationRulebook.initialPoints(role)` 决定：`Role.TEACHER` 为 1000，其他角色为 0。当前 `AdminUserService.changeRole` 只修改角色并写审计，不发布事件；因此学生被提升为教师后，其声誉账户仍保持开户时的积分。这是本轮明确接受的边界，不视为缺陷。

4. **计分与徽章的幂等放在记账服务内，不放在事件处理器内。**
   `ReputationLedgerService.record` 先按"事件标识 + 用户 + 计分原因"查重，再改余额、追加流水、发布 `ReputationChangedEvent`；采纳类计分还会用 `countByUserAndReason` 统计采纳数并授予"初露锋芒 / 助人十次"徽章，声誉达到 100 / 1000 时授予里程碑徽章。事件处理器只负责解析事件与编排调用。

5. **事件重放必须安全。**
   手工把 `outbox_event.published_at` 置空触发重放时，余额、流水、徽章、悬赏结算都不得重复变化。

## 备选方案与取舍

| 方案 | 优点 | 不采用的代价 |
|---|---|---|
| 声誉侧同步调用 `IdentityApi` 查角色 | 数据总是最新 | 引入同步耦合，身份库不可用时声誉也开不了户，违反上下文边界 |
| 让身份侧直接写声誉账户 | 链路短 | 跨上下文写库，破坏模块化单体的边界与事件驱动模型 |
| 角色变更时发事件并重算初始积分 | 语义完整 | 需要定义"降级是否扣分"等新规则，本轮无验收依据，先记为后续决策 |
| 只在内存里做幂等 | 实现简单 | 进程重启后失效，重放会重复计分 |

## 后果

- 正：开户链路完全不依赖身份模块在线；重放安全；徽章与计分规则集中在记账服务，测试只需覆盖一处。
- 负：角色变更后初始积分不自动调整，需要在用户手册或答辩说明中如实说明；管理员调整角色后，如涉及声誉，需人工处理或在后续 Sprint 补一个受控事件。
- 风险：`UserRegisteredEvent` 的 `role` 字段是开户语义的一部分，未来若身份侧改为"注册时一律学生、后续认证转教师"，本决策需要重新评估。

## 验证方式

应用层测试（在 `co-reputation-application` 内，不依赖容器）：

1. 同一 `UserRegisteredEvent` 连续调用两次处理器：账户只有一条，积分不翻倍；
2. 教师角色事件：账户初始积分为 1000；
3. 学生角色事件：账户初始积分为 0；
4. 采纳事件处理一次：回答者 +15，且获得"初露锋芒"徽章；
5. 自问自答被采纳：增量为 0，不写流水。

端到端验证（需容器环境，在持续集成上执行）：`CampusOverflowFlowIT` 中"采纳后徽章包含 `FIRST_ACCEPTED`"的断言通过。
